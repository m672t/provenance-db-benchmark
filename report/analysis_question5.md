# سؤال ۵: مقیاس‌پذیری و طراحی سیستم در حجم یک میلیارد رکورد

نتایج پروژه نشان داد که PostgreSQL و Neo4j برای نوع متفاوتی از بار کاری مناسب‌اند. بنابراین در مقیاس یک میلیارد رخداد، نمی‌توان یک پایگاه داده را برای همه Queryها انتخاب کرد.

## رفتار PostgreSQL

PostgreSQL در Queryهای آماری و زمانی مانند Beaconing و Threat Scoring عملکرد بهتری داشت. این Queryها بیشتر شامل:

```text
Scan
Group By
Window Function
Sort
Aggregate
```

هستند و PostgreSQL برای این نوع عملیات بهینه است.

در حجم یک میلیارد رکورد، اگر Query بدون محدودیت زمانی روی کل تاریخچه اجرا شود، هزینه Scan، Sort و Aggregate بسیار زیاد خواهد شد. برای کنترل آن باید از موارد زیر استفاده شود:

- پارتیشن‌بندی جدول رخدادها براساس زمان
- Partition Pruning
- Parallel Query
- ایندکس زمانی مناسب
- Summary Table یا Materialized View
- محاسبه افزایشی Threat Score و Beaconing

در Queryهای مسیر عمیق، PostgreSQL باید چند Join متوالی یا Recursive CTE اجرا کند. Q1 نیز نشان داد که مسیر شش‌گامی تعداد زیادی ردیف میانی و فایل موقت تولید می‌کند. بنابراین با افزایش عمق و درجه گره‌ها، افت عملکرد می‌تواند شدید باشد.

## رفتار Neo4j

Neo4j برای Queryهای مسیرمحور مانند Blast Radius و مسیر شش‌گامی مناسب‌تر است. در Q1 نیز Neo4j چند برابر سریع‌تر از PostgreSQL بود.

اگر گره شروع مشخص، عمق محدود و درجه گره‌ها کنترل‌شده باشد، هزینه پیمایش بیشتر به اندازه زیرگراف قابل دسترس وابسته است، نه کل پایگاه داده.

بااین‌حال، Neo4j در برابر انفجار تعداد مسیرها یا روابط میانی مصون نیست. Q2 نمونه واضح آن بود: با وجود کمتر از یک میلیون رابطه، بیش از 264 میلیون ردیف میانی ایجاد شد و زمان اجرا به حدود 50 ثانیه رسید.

در Queryهای سراسری مانند Q3 و Q4 نیز Neo4j مجبور شد تقریباً همه روابط را پیمایش و سپس Sort یا Aggregate کند. در مقیاس یک میلیارد رکورد، چنین Queryهایی نباید مستقیماً روی کل Graph فعال اجرا شوند.

## مقایسه

| نوع بار کاری | گزینه مناسب‌تر |
|---|---|
| مسیر چندگامی از یک گره مشخص | Neo4j |
| Blast Radius و Lateral Movement محدود | Neo4j |
| تحلیل زمانی و آماری | PostgreSQL |
| Threat Scoring و Dashboard | PostgreSQL |
| تاریخچه کامل و آرشیو | Data Lake / Object Storage |
| Query بلادرنگ | داده خلاصه‌شده یا Window محدود |

## معماری پیشنهادی

برای یک IDS جامع، معماری ترکیبی مناسب‌تر است:

```text
Sensors
   ↓
Message Broker
   ↓
Stream Processing
   ├── Data Lake
   ├── PostgreSQL / Analytical Store
   ├── Neo4j Active Graph
   └── Feature & Threat Score Store
```

### PostgreSQL

برای نگهداری رخدادهای ساخت‌یافته، تحلیل زمانی، Beaconing، Threat Score و Dashboard استفاده شود.

داده‌ها براساس زمان پارتیشن‌بندی شوند و امتیازها به‌صورت دوره‌ای یا افزایشی به‌روزرسانی شوند، نه اینکه در هر درخواست از ابتدا روی یک میلیارد رکورد محاسبه شوند.

### Neo4j

فقط Graph فعال و مرتبط نگهداری شود، برای مثال:

- رخدادهای چند روز اخیر
- Incidentهای فعال
- دارایی‌های پرریسک
- همسایگی چندگامی گره‌های مشکوک

به این ترتیب Queryهای مسیر روی یک زیرگراف کوچک‌تر و مرتبط‌تر اجرا می‌شوند.

### Data Lake

کل تاریخچه خام در Object Storage ذخیره شود تا برای آرشیو، تحقیقات جرم‌شناسی، آموزش مدل و Replay قابل استفاده باشد.

### پردازش جریانی

ویژگی‌هایی مانند تعداد Processهای یکتا، تعداد Execute و Write، فاصله زمانی ارتباط‌ها و Threat Score به‌صورت Incremental محاسبه شوند.

## نتیجه‌گیری

در مقیاس یک میلیارد رکورد:

- PostgreSQL برای Aggregate، Window و Queryهای زمانی مناسب‌تر است.
- Neo4j برای traversal محدود و رابطه‌محور مناسب‌تر است.
- PostgreSQL در مسیرهای عمیق با Joinهای متوالی افت شدیدی خواهد داشت.
- Neo4j نیز در گره‌های پر‌درجه و الگوهای پرFan-out ممکن است دچار انفجار محاسباتی شود.
- ایندکس و Cluster به‌تنهایی مشکل Query سراسری را حل نمی‌کنند.
- بهترین طراحی، ترکیب PostgreSQL، Neo4j، Data Lake و پردازش جریانی است.

این معماری باعث می‌شود هر نوع Query روی موتور مناسب اجرا شود و از اجرای محاسبات سنگین روی کل یک میلیارد رخداد جلوگیری شود.
